# 悬停卡片「缺一角」排查记录

现象：鼠标划过桌面卡盒，卡片铺开或放大时，某一张卡的一个角会**缺掉一小块**，
持续几帧后自己补回来。静止状态下永远是完整的。报告时间是 2026-09-22，批次 K。

下面按真实的顺序记录，包括走错的路。

## 1. 为什么会被裁掉

卡片层是一个全屏透明窗口，用 `SetWindowRgn` 交给 Windows 一堆矩形（span）来声明
「这些像素是我的」。这个区域同时决定两件事：

- 区域外的事件穿透到桌面（这是不切换 `WS_EX_TRANSPARENT` 也能做到点击穿透的办法）；
- **区域外不绘制。**

第二条是全部麻烦的来源，也是 Electron 版没有的约束：在 Electron 里区域只管输入，
裁多了只是「点不到」；在这里裁多了是「看不见」，屏幕上真的少一块，露出桌面。

所以「卡片缺一角」不是 CSS 的问题，任何 `overflow`、`box-shadow`、`transform` 的
改动都不可能修好它——是窗口区域在那几帧里比卡片小。

## 2. 区域是怎么算出来的

`buildSpans()` 遍历当前可见节点（卡盒、铺开的卡片、模态、小票机），取
`getBoundingClientRect()`，倾斜的卡片按扫描线切成 4px 高的梯形条带，最后交给
`SetWindowRgn`。推送在 `pushShape()` 里合并：**最快 40ms 一次**。

静止时每个矩形只加 `SHAPE_PAD_REST = 8` px；动画进行中加 `SHAPE_PAD_MOVE`。

## 3. 第一次尝试：加大动画 pad（无效）

推理是「卡片在动，区域没跟上，那就把动画期间的 pad 加大」。`SHAPE_PAD_MOVE` 从 60
提到 90。用户回复：还有。

事后看，这个方向本身就没有希望：一张卡从卡盒飞到桌面是 ~460ms 走 200px，也就是
每 40ms 移动 17px；而飞行途中它自己的盒子和缩放都在变。固定 pad 是**以当前位置为
圆心扩一圈**，卡片往哪飞，哪一边就不够。

## 4. 第二个发现：我的自检是个恒等式

排查期间一直在引用 `regionLeaks()` 的读数，它返回 `tight`，我据此说过
「claimed=16/16，leaks=tight」。这个自检是坏的：

```js
// 修之前
const spans = buildSpans();          // 用实时几何重算一遍
return anyCornerOutside(spans, liveBoxes());  // 和同一份实时几何比
```

两边都是**当下**的 DOM 测量，永远一致，所以它不可能报出任何泄漏。更要命的是
400ms 的自愈看门狗依赖它，于是那个看门狗从未触发过一次。

改法是比较**两个独立的东西**：把真正交给系统的那份 spans 存下来（`lastPushed`），
自检拿实时几何去问「这些角在不在已经被声明的区域里」。同时新增
`tests/clip-frames.js`：每个 `requestAnimationFrame` 采一次样，一次 pop 五千多帧里
抓到 **60 个坏帧**，card0 的左上角从 x=1700 一路追到 x=1498。

这是这条线上第一个能看见三帧问题的探针。在此之前所有「没问题」的结论都作废，
包括我自己报过的那些。

## 5. 三次修补，以及每次的读数

问题重新表述：区域不能只是「跟着」像素，必须**跑在**像素前面。

拖动路径上早就有现成的解法——`dragSweep`：一次抓取期间累积盒子**去过**的所有位置，
松手才丢。把它推广到每一张动画中的卡片：

| 改动 | 坏帧数 |
| --- | --- |
| 基线（实时几何 + 90px pad） | 60 |
| `sweptBoxes`：累积 500ms 内每个节点去过的位置 | 32 |
| 加速度前瞻：`LEAD_MS = 90`，上限 `LEAD_CAP = 260` px | 31 |
| `learnSpread()`：记住上一次稳定散布的外接矩形，动画期间整块盖住 | **4** |

第三条几乎没有收益，这一点要说清楚：从 32 到 31 基本是噪声。真正有用的是第一条
（历史）和第三条（目的地）。

剩下的 4 帧全部集中在**开机后的第一次**铺开——那时候 `spreadEnvelope` 还是空的，
没有「上一次」可以参照。第二次、第三次铺开的读数是 0。

## 6. 为什么「最后显示是完整的」

动画结束时 `scheduleSettle()` 会再切一次区域，用的是没有 pad 的贴合几何。所以稳定
态必然正确，缺陷只存在于飞行途中。用户描述的「只是一瞬间」和这里的机制是同一件事，
这也解释了为什么截图几乎抓不到它：截图的时间分辨率比一次 pop 还粗。

## 7. 还剩的问题，和清零要付的代价

要把最后 4 帧也干掉，唯一的办法是在动画**开始之前**就知道每张卡的目的地，也就是
改散布的排布函数（`placementFor` / `defaultPlacement`），让区域由预测的落点驱动，
而不是由已经画出来的盒子驱动。这个改动的风险清单单独列给用户评估，见提交说明；
核心矛盾是：预测的矩形一定比真实的胖，而**在桌面上多占一块矩形，就等于从桌面图标
那里抢走一块可点击区域**。现在这套机制（`SHAPE_PAD_REST = 8`、动画后立刻收紧、
`setIgnore` 空区域）所有的努力都朝相反的方向走。

## 8. 可以带走的两条

- **自检必须是两路独立的。** 用同一份数据自己跟自己比，得到的「一切正常」比没有
  数据更危险——它会让你停止怀疑。
- **三帧的问题不能用一秒一次的采样来验证。** 观测的时间分辨率低于故障时长时，
  故障不会表现为「小」，会表现为「不存在」。
